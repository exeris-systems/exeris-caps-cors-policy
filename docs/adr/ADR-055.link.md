# ADR-055 — Cap-tier Wall Guard (link stub)

**Authoritative copy:** [`exeris-tooling/docs/adr/ADR-055-cap-tier-wall-guard.md`](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/adr/ADR-055-cap-tier-wall-guard.md)

ADR-055 is a **per-repo** decision owned by `exeris-tooling` (tooling scope), with cross-repo
consequences for every cap. It is the tooling-side realization of ADR-024 validation predicate 4 (as
ADR-038 is its SDK-side realization): a JDK-standard `java.lang.classfile` scan over the compiled cap
classes, wired into `exeris:verify-capabilities` at `process-classes`, rejecting imports of
host-runtime packages (`org.springframework.*`, `io.netty.*`, `reactor.*`, `jakarta.servlet.*`),
kernel internals (`eu.exeris.kernel.**.internal.**`), and *sibling*-cap internals
(`eu.exeris.caps.<other>.internal.**` — a cap's own internals stay legal).

## Why this stub exists

This repository is **the first cap the guard actually runs against**. Every `mvn verify` here prints

```
Enforcing cap-tier Wall over .../target/classes (own cap(s): [corspolicy])
Cap-tier Wall clean (1 module(s), 6 class(es))
```

and that `own cap(s)` set is not configuration — `CapTierWall` derives it from **the segment after
`eu.exeris.caps.`** in the compiled package names, and that derived name is what licenses this build
to read its own `internal` packages. The package root is therefore load-bearing rather than tidy: a
rename, or an extra path segment, silently revokes the licence and turns this cap's own internals
into a sibling's. Nothing in the source says so, which is why it is written down here.

## When to consult ADR-055 from this repo

- **Any package rename or restructure** under `eu.exeris.caps.corspolicy`, for the reason above.
- **Any new type in `..internal`.** The split is mechanically enforced across cap boundaries, but the
  guard scans bytecode — it catches a sibling cap importing this one's internals, not an `internal`
  type leaking through an `api` signature inside this jar. That second failure is a review concern,
  and it is the more likely one here.
- **Any dependency addition.** The forbidden set is about *imports*, so a dependency that never
  appears in a signature can still fail the scan the moment a method body touches it.
- **Reading the rule versus running it.** Where the ADR text and `CapTierWall` disagree, the guard is
  what runs. Read
  `exeris-tooling/exeris-codegen-java/src/main/java/eu/exeris/tooling/codegen/java/**/CapTierWall*`
  before arguing about the boundary.

## Pending amendment

`ROADMAP.md` 0.2.0 carries a documentation-only amendment to this ADR's rationale, to be raised
against `exeris-tooling` as its owner: `exeris-kernel-core` is **tier-neutral** — shared by the
Community and Enterprise drivers alike — so it is callable from a cap, and only `**.internal.**` is
forbidden. `CapTierWall` already implements exactly that; what is wrong is the surrounding prose in
ADR-024 and the capability author guide, which say that only the SPI surface is callable. A guard and
its documentation disagreeing about what is legal is the condition under which authors write to the
stricter reading and lose access to something they were entitled to use.
