# ADR-053 — SKU Composition Manifest Format (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-053-sku-composition-manifest-format.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-053-sku-composition-manifest-format.md)

ADR-053 is a **cross-repo** decision owned by `exeris-docs` (platform scope). It fixes JSON as the
composition manifest format, with the schema owned by `exeris-sdk-composition-spec` and the canonical
reader by the `exeris-tooling` pipeline. It resolves the *format* half of ADR-024 open follow-up 3;
signing detail stays delegated to the `exeris-sku-*` repository convention.

## Why this stub exists

`src/main/generated/java/cap-manifest.json` is emitted by this build, **committed to this
repository**, and is the artefact a SKU actually consumes. It is the only output of the whole
capability pipeline that outlives the build, so its shape is a contract this repo participates in
rather than a build by-product it happens to leave behind.

## When to consult ADR-053 from this repo

- **Any change that regenerates the manifest.** `schemaVersion` is `2`; a diff that changes it is a
  format change, not a rebuild. `exeris:generate` writes into `src/main/generated/java/`, not
  `target/`, and regeneration is byte-stable — a dirty `git status` after `mvn verify` means the
  declaration and the committed manifest disagree.
- **Reading the stamp.** `stamp.validated: true` and a `sha256:<64 hex>` `contentBinding` are the two
  fields that carry weight. The binding is what makes the stamp non-transferable: it attests *this*
  composition rather than some composition. CI asserts both explicitly in
  `.github/workflows/build.yml`, because "the goal ran" and "the goal produced a valid stamp" are
  different claims and only the second one matters to a SKU.
- **`compositionVersion`.** It reads `0.0.0` here because the codegen plugin does not yet wire it
  (tracked as tooling **U3**); the SDK's stamp asserter tolerates that by design. Do not "fix" it in
  this repository — the field is written by the plugin, and a hand-edited manifest is exactly the
  drift the content binding exists to detect.
- **Proposing a new field.** The schema is owned by `exeris-sdk-composition-spec`. A field that
  appears only in this cap's manifest is unreadable to the canonical reader, so the change belongs
  upstream in the SDK and tooling first, and reaches here as a regenerated file.

## Engineering status

ADR-053 is **ACCEPTED** (2026-07-21). The first enforced artefact ships with the
`exeris-sku-api-gateway` scaffold; until a SKU consumes this cap's manifest, the committed file is
validated but not yet exercised end to end. `ROADMAP.md` 0.4.0 is where that changes — publishing a
resolvable artefact is what first puts this manifest in front of a real reader.
